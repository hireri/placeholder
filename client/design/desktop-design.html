Metrolist · desktop client

Architecture, design language and shell layout for the GPUI app

Three processes, one set of tokens that every theme maps onto, and one window layout built around keyboard use and cover art. Everything here is a proposal to push on; open questions are at the bottom.

1 · Architecture

The UI is Rust. Everything that talks to YouTube or Spotify stays in Kotlin.

The Kotlin backend already works and breaks whenever YouTube changes, so it stays a separate daemon that the app spawns. The GPUI process only renders, plays audio and stores credentials. Login runs in its own small window because the wry spikes worked in a separate process on Wayland, while the webview embedded in gpui does not support native Wayland.

Transport: JSON-RPC over stdio

The app spawns the daemon and talks newline-delimited JSON-RPC on its stdin and stdout. There is no port to pick, no auth to design and it behaves the same on Linux, Windows and macOS. Streaming results (search, playlist pages) and events (queue changed, token refreshed) come back as notifications on the same pipe.

Credentials stay with the client

The login helper returns YouTube cookies and the Spotify sp_dc cookie to the app. The app stores them in the OS keyring and sends them to the daemon on start. The daemon mints Spotify tokens itself, since that logic already lives behind a Kotlin interface.

The daemon resolves, the client plays

Playback asks the daemon for a stream URL with its headers and expiry. The client then streams it directly, so audio never passes through the pipe, and a daemon crash does not stop the song that is playing.

Pin everything

gpui is pre-1.0. gpui-component pins an exact gpui snapshot, so the app should pin that exact pair and treat upgrades as planned work.

2 · Design language

Quiet tonal surfaces. The cover art supplies the colour.

Spotify leads with dense dark cards and a loud accent; Apple Music leads with large white art and red. Metrolist takes neither. It uses flat tonal surfaces that are tinted by the theme, one restrained accent that only marks what is playing or focused, and a single header wash taken from the artwork. Type does the work that borders and shadows do elsewhere.

Tone separates, lines don't

Regions are four steps of one tinted ramp: window, sidebar, panel, hover. There are no 1px dividers between regions. The only soft edge is a short fade where lists scroll out of view.

One accent job

Accent means "this is playing" or "this has focus". Buttons, links and tabs stay in neutral tones, so the accent is always meaningful.

Art is the only decoration

Artwork has a 6px radius and a soft shadow. Album and artist headers get a faint wash from the accent hue, and the player card fades its cover into a blurred copy of itself. Nothing else gets a gradient.

Keyboard first

The app is a desktop tool. Ctrl/⌘ K opens a palette for search, navigation and commands. Space, arrows and / behave as in a file manager. Every row can be reached without a pointer.

Press responds, release commits

Rows and buttons change on pointer-down with a 90 to 100ms tonal shift. Hover is instant. Nothing waits on a transition before it accepts input.

Without blur

I'm assuming GPUI has no backdrop blur on all platforms, so no surface depends on it. The player's blurred backdrop is not one: the app blurs the cover once per track (shrink to about 32px, scale back up) and draws that as an ordinary image. Layers are opaque tonal steps; only the content and the player float, each as a card with a shadow; the library sits directly on the window background.

Reduced motion swaps springs for a 150ms cross-fade and stops the playing-row bars. I haven't confirmed GPUI ships a spring primitive; if it only has easing tweens, we write a small spring driven by frame ticks so drags can hand their velocity over.

3 · Theming

A theme is a source colour, a mode and optional overrides.

The engine turns the source colour into every role in the table above, so a theme can be one line. A JSON preset is the same thing written to disk, with the right to override any role or radius. The shell below is built from exactly these roles; change the colour or pick a preset to see it move.

Derivation

Hue comes from the source. Neutrals borrow it at very low chroma (about 0.014 in OKLCH), so surfaces feel related to the accent without looking tinted. The accent keeps the source chroma at a fixed lightness per mode. Any text role below 4.5:1 against its surface is nudged until it passes, and the nudge is logged so a preset author sees it.

The roles map onto gpui-component's theme colours instead of replacing them; it already loads themes from JSON, which I'd verify before settling the schema.

    4 · Layout
    
A titlebar, a collapsible library on the left, content in the middle and the player on the right.

    
The player is the phone player from your screenshots, kept as a column: cover and controls by default, with the cover swapping for lyrics or the queue while the transport stays put. That removes the need for a separate bottom bar and for any now-playing side panel. Try the three buttons at the bottom of the player and the collapse button on the library. Drag the edge of either sidebar to resize it (double-click resets, arrow keys nudge): the library goes from 200 to 360px, the player from 260 to 400px, and the content never drops below 380px, so the player card always keeps its right edge and margin on screen. The buttons above the shell jump between pages; the left-hand page buttons, library items, the account menu, the status island, Enter in the search box and Ctrl K all navigate too.

Titlebar · 52px
The logo sits at the left edge, over the library, tinted with the accent. Back and forward sit beside one search pill that opens the command palette, the single place to search YouTube Music and run commands; the library has its own search for saved items only, so the two never compete. The right side holds one island that is the notifications button and widens into the Spotify import progress while an import runs, the listening party button and the account menu, which is also where the theme and settings live.

      
Player · 308px card, right
The player is its own card, like the content, with a 10px gap between them. The cover is the default view: it runs the full width of the card and its lower edge fades into a blurred copy of itself that fills the card, which is always dark so text stays legible on any art. Lyrics and Queue each replace it with a compact header (small cover, title, artist, favourite, more) and keep the scrubber, transport and volume in the same place, so nothing the thumb or cursor learned moves. The top half of the card is one flexible slot for the cover, the lyrics or the queue; the scrubber, transport, volume and bottom row stay anchored below it in every view, so nothing there moves when you switch. In Lyrics and Queue the title row slides up beside a small cover (the big cover shrinks into it) and the list fills the slot under it. The bottom row switches views; the middle of that row is a three-part pill for shuffle, repeat and endless, which keeps adding recommendations when the queue ends (the queue previews them under "Endless"). The header above the cover holds the album name and the button that collapses the player. Collapsing slides the card to the right until only a 56px sliver is left at the window edge: the left edge of the cover and its blurred backdrop, under a fade that is part of the card, so it slides in with it, solid on the left and still 60% opaque on the right, with a chevron in the middle. The whole sliver is the button that reopens it. A small floating pill centred on the window then carries cover, title, previous/play/next, a thin progress line, and Lyrics and Queue buttons that reopen the player on that view; tapping the cover or title reopens it on the cover. Volume and the scrubber live in the full player. The whole card scrolls: a square cover, the controls under it, then two info cards (About the artist with a Follow button, and Credits), so a tall player has no dead space and a short one just scrolls. The cards stay under the controls in Lyrics and Queue too; there the lyrics or queue keep at least 380px and the card scrolls to reach them.

      
Content
The header wash is the one place colour from art appears. Track rows are 44px with tabular durations and a tonal hover. The playing row is the only one with accent text. Rows virtualise, since Liked Songs can pass 5,000 items.

      
Library · 264px, left
Four page buttons (Home, Downloads, Local Music, History & stats) sit at the top; there is no separate Library page, because the list below them is the library, then the library with its own search, a sort and view button, filter pills and a list that shows the open item. The button opens Sort by (recents, recently added, alphabetical, creator) and View as: compact list with a dot between title and subtext, the list with covers, a grid of covers only, or a grid with title and subtext under each. Its collapse button sits on the left of the header. Collapsing to 68px only trims text: every icon, cover and the button itself stay exactly where they were, the search stays as an icon, and the filter row shrinks to zero height.

    5 · Pages
    
Every page is built from the same few parts.

    
Pages reuse the shell, the 44px row, the cover-art header wash and one shelf of 132px cards, so a new page costs a layout rather than a new look. Nothing below adds a colour or a control the playlist page doesn't already have.

    

      
PageBuilt fromDecisions

      
        
HomeMood chips, quick-pick tiles, card shelves, feature cardsNo hero banner. Quick picks are the eight things you reopen most, as flat tiles (four across when the page is wide). Shelves scroll sideways. The page ends with large portrait cards, each labelled with why it is there ("More like Hoshi Yume"), art filling the card, and the other artists on it at the bottom.

        
SearchTop result, song rows, shelvesThe titlebar box searches YouTube Music; Enter lands here. Type chips narrow it. Library search stays in the sidebar.

        
ArtistWash header with round art, rows, shelvesPopular songs show play counts instead of the artist column. Artists are always round, albums square.

        
DownloadsStorage bar, progress rows, tableActive downloads come first and are the only place a progress bar appears. Quality and size are columns, not a settings trip.

        
Local MusicFolder chips, info bar, tableFiles that aren't matched to YouTube Music get one bar with a Match now action, not a warning on every row. A Format column shows FLAC depth and bitrate.

        
History & statsSource chips, stat tiles, panels, ranked lists, day-grouped rowsOne page for what you played and how much, across YouTube Music, Spotify and this app. The source chips filter every list and swap the totals; each row carries a YT, SP or ML badge. YouTube Music history comes from the account; Spotify is limited to what its web player exposes (recent plays, not full history); plays from this app, including local files and offline listening, are counted locally and are the only source that is complete.

        
SettingsCategory list, one panel at a timeAppearance is live: swatches, mode and density re-theme the shell behind it. Shortcuts are listed so they can be rebound later.

        
Spotify importProgress, tiles, review rowsEach uncertain track sits next to its best match with the reason it is uncertain. Accept or skip per row, or accept everything above 90%.

        
Listening partyPopover from the titlebarThe button sits beside the account pill and shows a dot while a party is live. Not in a party: start one or join with a code. In one: code and copy-link, who is listening and their sync state, two guest permissions, End party.

        
Palette and account menuOverlay, popoverCtrl K, / or the search pill. It is also the search box: empty, it lists recent searches; typing adds completions and a few songs, albums and artists above the matching commands. Arrows move, Enter runs. The menu holds settings, accounts, shortcuts and sign out.

    6 · Open questions
    
What I'd settle before building

    
    
      
  1. Audio engine. gpui has no audio. libmpv gives codecs and buffering for free but adds a native dependency; symphonia with rodio is pure Rust but means writing HTTP streaming and seeking. I'd prototype with libmpv.
    2. 
      
  2. Who owns the library database. If the daemon owns it, the client stays thin and the Android schema can be shared. If the client owns it, offline start-up is faster. I'd start with the daemon.
    3. 
      
  3. Packaging the JVM. A bundled runtime from jlink is the dependable route; a native build would be smaller but may not survive the InnerTube dependencies.
    4. 
      
  4. gpui versus gpui-component. The shell above needs lists, tabs, an input and a palette. gpui-component covers those on a pinned snapshot, but a hello-world on your machine should confirm it renders on Wayland before we commit.
    5. 
      
  5. Explore, Charts and Podcasts. Android has them as screens. I would leave them out of the first desktop release and let Home and Search cover discovery; say if any should get a sidebar button.
    6. 
      
  6. Login helper on Windows and macOS. Only Linux was tested; the helper design assumes wry behaves the same elsewhere.
